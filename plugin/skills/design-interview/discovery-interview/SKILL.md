# Discovery Interview — 기획·요구사항 인터뷰

새 프로젝트/기능의 **기획·설계 초입**에서 구조화된 인터뷰로 요구사항을 끌어내고,
그 답변을 추적 가능한 **정본 스펙 문서**로 정리한다. 이 문서들이 이후 UI 설계
(`design-system-docs` 스킬)와 구현의 근거가 된다.

## 언제 쓰나
"무엇을 만들지"가 아직 확정되지 않은 단계. 새 앱/기능 기획, 요구사항 정의, 범위·MVP
결정, PRD 작성. 이미 스펙이 있으면 이 스킬 대신 바로 설계로 간다(빈틈만 이 스킬로 보강).

## 진행 원칙
1. **한 번에 한 주제.** 아래 8개 영역을 순서대로 다룬다. 한 턴에서 서로 관련된
   질문을 최대 3~4개까지만 묶고, 다음 영역으로 넘어가기 전에 답을 반영·확인한다.
2. **선택지로 묻는다.** 결정형 질문은 Codex의 사용자 입력 도구를 사용할 수 있을 때
   2~3개의 상호 배타적인 선택지로 묻고, 추천안을 첫 번째에 "(추천)"으로 표시한다.
   해당 도구를 사용할 수 없는 실행 모드에서는 같은 내용을 짧은 일반 질문으로 묻는다.
   열린 질문(문제·목표·에피소드)은 자유서술로 받는다. 사용자가 "네가 정해" 하면
   합리적 기본값을 골라 근거와 함께 명시하고 진행한다.
3. **가정을 드러낸다.** 답이 없는 부분은 임의 확정하지 말고 **Open Questions**에 적고,
   잠정 가정(assumption)을 표시한 뒤 계속 진행한다. 나중에 결정.
4. **추적성.** 모든 요구사항·화면·상태에 ID를 부여한다(REQ-*, SCR-*, FLOW-*, STATE-*,
   ENT-*, DEC-* 등). 이후 설계·구현이 이 ID로 근거를 참조한다.
5. **과도한 인터뷰 금지.** 사용자가 이미 말한 것을 되묻지 않는다. 명백한 것은 확인만.
   범위를 넓히지 말고 MVP에 집중한다.
6. **답이 얕으면 더 판다.** 일반적이거나 모호한 답변은 표면일 뿐이다 — 구체적 사례·숫자·
   에피소드 하나를 요청해서 다시 판다. "그게 왜 중요한가?"를 2~4회 반복해서 핵심까지
   내려가는 laddering, 또는 표면적 주장의 근본 이유를 캐는 5 Whys를 쓴다. 연속 두 번의
   탐침이 새 정보를 못 내면 그 주제는 충분한 것이다(포화 신호) — 다음 영역으로 넘어간다.

## 인터뷰 8영역 (순서)
각 영역의 대표 질문. 프로젝트에 맞게 취사선택한다.

1. **문제 · 목표 (왜)** — 어떤 문제를 누구를 위해 푸는가? 지금 그 사람은 어떻게
   대처하고 있나(현행 대안)? 성공하면 무엇이 달라지나? 왜 지금인가 — 무엇이 바뀌어서
   지금 가능해졌거나 필요해졌나? 예산·시간이 무제한이면 어떤 모습일까(10-star 버전) —
   그 방향과 지금 정하는 MVP가 같은 길 위에 있는지 나중에 확인할 기준으로 남겨둔다.
2. **대상 사용자 · 사용 맥락** — 1차 사용자는? 언제·어디서·어떤 조건에서 쓰나
   (모바일/데스크톱, 실내/야외, 한 손/급함, 온라인/오프라인, 빈도)?
3. **핵심 가치 · 성공 지표** — 이 제품의 한 문장 가치는? 성공을 무엇으로 측정하나
   (핵심 행동 완료율, 재방문 등)? 반드시 지켜야 할 품질(신뢰·속도·프라이버시)?
4. **범위 · MVP** — 반드시(Must)/있으면 좋음(Should)/나중(Could)/안 함(Won't)으로
   기능을 가른다. MVP에서 의도적으로 **빼는 것**을 명시한다. **안티골(anti-goal)**도
   같이 적는다 — 이번엔 절대 안 만들 것, 유혹적이지만 의도적으로 배제하는 것. 스코프가
   슬금슬금 늘어나는 걸 막는 가장 확실한 문서다.
5. **핵심 플로우 · 화면** — 사용자가 목표를 이루는 주요 경로(진입→행동→결과)를
   단계로 적고, 각 단계의 화면(SCR-*)과 분기를 뽑는다. empty/loading/error 경로 포함.
6. **데이터 · 상태** — 핵심 엔티티(ENT-*)와 관계, 소유·공유 단위. 시간에 따라 변하는
   대상의 상태값(STATE-*)과 전이(생성 중·완료·실패 등).
7. **제약 · 비기능** — 플랫폼(iOS/Android/Web), 오프라인, 프라이버시/규정, 인증, 예산,
   기술 스택 선호, 일정, 접근성 요구. 파괴적/되돌릴 수 없는 동작 여부.
8. **리스크 · 미해결** — 가장 불확실한 가정, 실패하면 치명적인 부분, 아직 못 정한 결정.

## 산출물 (정본 문서)
인터뷰가 충분히 진행되면 대상 프로젝트의 `docs/`(또는 지정 위치)에 아래를 만든다.
프로젝트 규모에 맞게 파일을 합치거나 나눈다. 각 문서는 번호·ID로 상호 링크한다.

```
docs/
  00_project_brief.md     문제·목표·사용자·가치·성공 지표 (영역 1~3)
  01_requirements.md      REQ-* 기능/비기능 요구사항 + Must/Should/Could/Won't (영역 4·7)
  02_ui_flow.md           FLOW-* 사용자 경로 · SCR-* 화면 목록 · 진입/분기 (영역 5)
  03_screen_contract.md   화면별 가시 의무·행동·상태(SCR별 계약) (영역 5)
  04_data_model.md        ENT-* 엔티티·관계·소유 단위 (영역 6)
  05_state_machine.md     STATE-* 상태값·전이·불변식 (영역 6)
  06_open_questions.md    미해결 결정 · 가정(assumption) · DEC-* 결정 로그 (영역 8)
```

`assets/`의 템플릿을 복사해서 채운다. 문서를 만든 뒤 프로젝트 docs 인덱스(있으면)에
링크를 추가한다.

## 다음 단계로 연결
스펙이 정리되면 UI 설계는 **`design-system-docs` 스킬**로 이어간다 — 그 스킬은 여기서
만든 SCR/FLOW/STATE/ENT/REQ 문서를 "정본"으로 참조해 와이어프레임·컴포넌트·토큰을
만든다. 두 스킬은 기획(이 스킬) → 설계(그 스킬) 파이프라인을 이룬다.

## 작업 순서
1. 프로젝트에 기존 자료(메모·기존 문서·유사 앱)가 있으면 먼저 읽는다.
2. 8영역을 순서대로 인터뷰한다(사용 가능한 사용자 입력 방식으로 한 주제씩).
3. 영역이 끝날 때마다 요지를 짧게 되짚어 확인한다.
4. 충분히 모이면 `assets/` 템플릿으로 정본 문서를 작성한다(미결정은 Open Questions로).
5. 요약과 다음 단계(설계 착수 여부)를 제안한다.
